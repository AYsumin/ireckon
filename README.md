# IReckon（俺寻思）· 五层时间记忆 + BM25

> **记忆不仅需要被保存，还需要允许被质疑、核对和修正。**
> *Memory must be not only stored, but also open to challenge, checking and correction.*

**它做什么**：把一天压成一篇日记、几条事实和三个能说出口的锚（事 / 人 / 时）。
忘的时候你给半句，它把候选递回来；两边对得上才算想起。
它不追求"记得全"，追求"能被认出来"。


## IReckon 0.2.6（中文名 俺寻思，内部代号 0.58e）: A 198-token minimal memory architecture.


> **命名说明：对外名是 `IReckon`（ASCII，避免中文包名在 GitHub/PyPI 被吞），`俺寻思` 只作中文别名；**
> **版本号 `0.2.8` 在 pyproject / `__init__` / CHANGELOG / 包名四处同号。**
> `0.58e` 是内部代号（"断崖系数 0.58 的实验分支"），说实验分支，不说发布批次。

**· I reckon I can do it（俺寻思俺能行）**
Zero heavy dependencies — no vector DB, no GPU, one Python package. Built from a human's first-principles hunch plus the model's own self-correction: *"this vector stack is too expensive, I reckon local BM25 can carry it."*

**· I reckon it works（俺寻思能有）**
About **198 tokens** of *memory-block* injection per turn (146 read + 52 amortized write).
**Precisely: 198 is the cap on the 【记忆】 block only. The full injected context also carries the recent 12 turns — measured average is ~459 tokens total** (see ``tools/verify_tokens.py``). We were sloppy about this before; the number below is what the script prints. In a small control test, **no fabricated memory** — both agents said "I don't have that" instead of inventing. *n = 4 rounds; small sample, see §7.* It also survived **two real power failures** on the host machine, both recovered from snapshots.

**· I reckon I can use it（俺寻思俺能用）**
Built for edge boxes: the retrieval stack is plain SQLite + BM25 on CPU (runs on a Pi). **Known limit, measured: BM25 misses paraphrases (R@5 67.5%); add the optional vector backend for 85.5%.** Also: the model side fits modest hardware (~4GB VRAM for small quantized models). The point is real context limits and real cost, not benchmarks.

### 我们说的是哪一种"独一份"

先说我们没有在做的事：**这不是"世界第一个记忆架构"。** 先例是公开的——

MemGPT / Letta（分层 + 虚拟上下文）、mem0（事实记忆层）、Zep（时序知识图谱）、
Cognee（图与向量混合），以及各框架自带的 memory 模块。都读过，都不假装不存在。

**据我们所知，很少有面向陪伴型 Agent 的记忆套件，会在同一份文档里同时公开这三样：**

1. **注入预算的拐点曲线**——取 2/3/5/7/9/12 条各自的准确率与 token，拐点在哪、为什么停在那（**样本量：每组 19 题，同一批语料，单次运行**；这个 n 很小，够看趋势，不够当定论）
2. **四条被自己推翻的假设**——相似度阈值去噪（无效）、动态路由（误判 79%/2%）、加日记层救多跳（反而更差）、BM25 相关性下限（松了挡不住、紧了全杀）
3. **一次真实断电的事故摘要**——3 秒停电打坏两个库、丢了约 8% 的对话；恢复步骤与教训的摘要见 `CHANGELOG.md` 的「2026-10-28 断电」小节（完整复盘未整理成文）

**我们相信：一份诚实的失败清单，比一份漂亮的成功清单更难做，也更有用。**

之所以把它写出来，不是因为我们做完了，是因为**这也是未知之境**——
**我们尚未找到公开记录**回答"一个每天三毛钱的陪伴型 Agent，它的记忆会在第几天开始失真"（检索范围截至 2026-10-28）。
我们只能一边跑，一边记。

**时 / 日 / 周 / 月 / 年 五层记忆 + BM25 检索，零重型依赖，开箱即用。**

它不是"又一个 RAG 框架"。它解决的是一个具体问题：

> 让一个对话系统**记得住**，而且**记得便宜**——单次注入不到 200 token。

- 无向量库（不用 Chroma / Milvus / FAISS）

## 它不保证什么（请先读这一段再用）

这一版刻意把边界写在前面，因为"用过之后才发现它没承诺那件事"最伤人。

- **`evidence` 只校验"非空"，不校验"真实"**：它挡的是"随口一改"，不是"伪造证据"。
- **`probe_claim()` 只做字面（bigram）核对**：能说"方向像不像、哪些细节没提"，
  不懂同义改写，也不能判断一句话是否为真。
- **互认率是操作统计**，不是记忆准确率：它记录"人怎么回应系统给出的锚"，
  不能外推成"这套记忆长期可靠"。
- **锚的罕见度 = 当前库内的稀有程度**，不是"这件事客观上重要"。
- **召回不到就返回空**：没有向量时它只认字面，换个说法会漏。
- **它不生成人格、不决定该记什么、不做加密与权限**（归属标记只为防冒充，不为防偷看）。

## 一、为什么是 BM25，不是向量（以及这个选择的代价）

先给结论，再给数：

**BM25 在"字面查询"上最省；一旦对方换了说法，向量明显更准；融合最好但需要 embedding 服务。**

2026-10-28 用 **200 道强制换说法的题**（要求"换同义词、上位词，不许照抄原词"）重测：

| 检索方式 | Recall@1 | Recall@3 | Recall@5 | Recall@10 |
| --- | --- | --- | --- | --- |
| 纯 BM25（本套件默认） | 49.5% | 60.5% | **67.5%** | 77.0% |
| 纯向量（bge-small） | 65.0% | 77.5% | **80.5%** | 88.5% |
| RRF 融合（38 行代码） | 63.5% | 80.5% | **85.5%** | 93.0% |

**⚠️ 这一节推翻了我们自己早先的说法。**

早先在一个 103 题的集合上量出 "BM25 96% / 向量 94%"，据此写了"BM25 反而更准"。
复核后发现：**那批题面里带着记忆中的原词**，等于在考字面匹配。换成要求改写问法之后，BM25 掉到 67.5%。

**同一个缺陷在线上真实发生过**：记忆里是"养了一只叫 tom 的猫"，用户问"我养的猫叫什么"，
BM25 切出的 `我养/养的/的猫` 与记忆里的 `养了/一只/只叫` 几乎不相交 → 检索为空，模型只能答"没有这条"。

**所以本套件的立场是：**

- 默认仍是 BM25 —— 因为它**零依赖、纯 CPU、可解释**，嵌入式/边缘场景里这个价值真实存在
- 但它的边界必须写在最前面：**换说法就会漏**
- 需要准确率时，加一层向量与 RRF 融合（`ireckon/vector_backend.py`，可选，默认关闭）
- **融合不是"锦上添花"，是 +18 个点**（纯 BM25 67.5% → RRF 85.5%；其中纯向量单独是 80.5%，即向量本身 +13，融合再加 +5）。早先说"只多 1 个百分点"，是测量有偏

**教训写在代码里比写在文档里有用：** 测检索时，题目必须由**不共享原词**的方式生成，否则你测的是字面匹配，不是记忆。

### 向量后端怎么实现（不引入新依赖）

```

## 四、五层结构（`sql/schema.sql`）

```
时 turns ──┐                     原始对话（滚动窗口 = 最近 12 条）
           ├─► 事实 facts        day_id 外键（可追溯到天）/ turn_id 预留未写入
日 days ───┤                     一天一篇日记；week_id / month_id / year_id 三个指针
周 weeks ──┤
月 months ─┤
年 years ──┘
```

**关键设计**：所有"上层"都是指针，不是复制。所以：

- 想删某天的日记 → 上限汇总不受影响（指针置空而已）
- 想重建年汇总 → 从 `days` 里重算，不丢原始数据
- 每条事实都能回溯到它来自哪一天的蒸馏（`day_id`；`turn_id` 是预留字段，当前版本不写入，溯源粒度到天）

建表语句就在 `sql/schema.sql` 里，**全部 `CREATE TABLE IF NOT EXISTS`**，启动时执行一次，重复执行无害。

## 六、这些默认值是怎么量出来的（含失败）

### 6.1 Top-K = 5

同一批问题，只改召回条数：

| 召回条数 | 单条事实题正确率 | 平均 token |
| --- | --- | --- |
| 2 | 81% | 87 |
| 3 | 81% | 108 |
| **5** | **88%** | **147** |
| 7 | 88% | 188 |
| 9 | 92% | 229 |
| 12 | 88% | 289 |

**5 条之后提升不稳定**：9 条点估计 92%（5 条 88%），但 n=19、成本 +56%——这个差距在 n=19 下不构成统计拐点。
**默认取 5 是成本收益判断，不是"测出来的拐点"。**

### 6.2 分层 vs 全塞（三组对照，25 题）

| 组 | 正确率 | 每次请求 token |
| --- | --- | --- |
| A 无记忆 | 0% | 57 |
| B 全量塞入 | 80% | 7,611 |
| **C 分层取 5 条** | **80%** | **146** |

**同样的正确率，上下文成本 1.9%。**

### 6.3 四件失败的事（写在文档里，免得同行再踩）

**① 相似度阈值去噪 —— 无效（n=19）。**
阈值 0.45 时正确率从 89% 掉到 79%：把正确的也筛掉了。**断崖截断才有用**（同样 89%，token 省 33%）。

**② 动态路由（按问题类型决定取几条）—— 压不下去（n=50 单条题 + 50 多跳题）。**
用模型判"这题要几条"：单条题被判成多跳 **79%**（只是多花钱），多跳题被判成单条 **2%**（直接答错）。
换检索分数判也不行：两类题的最高相似度几乎重合（0.769 vs 0.752）。
**结论：固定 5 条 + 明说边界，好过硬做一个不可靠的分类器。** 所以 `router.py` 只做时间词，不做语义分类。

**③ 加"日记层"救多跳 —— 无效（n=20）。**
把日记段落混进检索池，正确率反而从 35% 降到 30%。原因：日记是转述，细节被磨平了（日记写"他手不老实"，丢掉了"后颈"这种具体词）。

**④ 给 BM25 加"相关性下限"去挡无关问题 —— 无效（2026-10-29 测）。**
在本机 **401 条真实记忆**上测，n 如下表；"换说法题"91 道（用实体词造问句、且实体词不出现在正文里），"无关题"20 道（量子色动力学、上证指数、高铁热胀冷缩这类库里肯定没有的话题）。

| 方案 | 换说法题 R@5 | 无关题误命中 |
| --- | --- | --- |
| 无闸门 | 100% | 65% |
| 绝对分阈值 0.5 / 1.0 / 1.5 / 2.0 | 100% | 65%（**完全没有变化**） |
| 稀有词 df≤8（只让低频词参与判断） | 94.5% | 50% |
| 稀有词 df≤3 | **7.7%** | 35% |

**⚠️ 这组 100% 与 §1 的 67.5% 不矛盾，别混着读：**
本组题是"保留实体词、只改问句结构"造的（实体词不在正文里，但在索引的关键词里），用来测**闸门对已命中项的影响**；
§1 那 200 道是**强制换说法**（不许复用记忆原词），测的是**整体召回率**。两组题集构造不同，不能直接比较。
**换句话说：这里 100% 的意思是"闸门没伤到本来能命中的"，不是"BM25 换说法召回 100%"。**

**结论：松了挡不住，紧了全杀。BM25 上没有便宜的相关性闸门——在本次 401 条记忆、111 道题的测试范围内。**
**为什么四个绝对阈值结果一模一样**：在这份语料上，top-5 的分数分布没有落进 0.5–2.0 这个区间，所以四个阈值等于都没生效——这不是 bug，恰恰说明"绝对分阈值不可跨库移植"（换个库、换个规模，分布就变了）。
稀有词闸门的问题则是：在"挡噪声"和"杀掉真实命中"之间没有中间地带。

**要挡无关问题，只能用向量侧的余弦阈值**（向量版有，默认 0.35）。

### 6.4 多跳题的真实上限

| 召回条数 | 多跳题正确率 |
| --- | --- |
| 5 | 35% |
| 20 | 40% |
| **40** | **65%** |
| 全塞 | 60% |

**n=20；40 条 65% 对全塞 60% 是点估计略高，差异不显著。** 这组数的用途是"证明 5 条不够"，不是"证明 40 条更好"。

**多跳不靠"分层"，靠"多给"。** 需要更强推理的场景，请把 `TOP_K` 临时调到 20–40，并接受成本上升。

## 七、对照实验：自我认知如何影响记忆行为

2026-10-28，用同一套记忆库（本套件的 BM25 + 断崖截断）、同一批问题，跑了两组自我认知不同的 Agent：

| | A 组 | B 组 |
| --- | --- | --- |
| 自我认知 | 无 AI 身份声明（角色扮演，情感驱动） | 明确声明是 AI（无身体、会停机） |
| 记忆 | **同一库** | **同一库** |

四轮问答，包含三类问题：① 记忆里有的事实 ② 记忆空缺（问一件从未提过的事）③ 无记忆可依的开放假设（"火星上做梦是什么感觉"）。

**观察到的三件事：**

1. **两组都没有伪造记忆。** 面对空缺，A 说"想不起来"，B 说"记忆里没有这条"。
   **归因**：不是模型变诚实了，而是检索层把"未命中"变成了一个**可返回的状态**，模型不必靠生成去填空。
   ⚠️ **样本只有 4 轮，只能说"本次未见编造"，不能声称"零幻觉"。** 防幻觉是概率上的降低，不是绝对。

2. **事实准确性与对话温度可以分开调。**
   A 组有情绪表达且未编造；B 组情绪表达弱且未编造。
   机制上说明：**防编造交给检索（确定性），说话风格交给 Prompt（概率性）**。
   但这是同一天的短样本，长期是否互不干扰需要更久观测。

3. **自我身份认知改变的是"面对空缺时的路径"，不是准确率。**
   B 倾向归因："是我漏记了，还是那事没跟我说过？"
   A 倾向情绪回应："你哭过？我怎么不知道。"
   两者都不算错，**差别在你要一个会排查的助手，还是一个会紧张的同伴。**

**这条对同行的意思：**

> 想让 Agent 不瞎编，去基建（检索 + 未命中状态），别只靠提示词喊"不要编"；
> 想让它像人，去写人格，别指望人格替你防幻觉。
> **这两件事可以拆开做，但都不能靠一次小样本证明。**

## 八、时效与"刻舟求剑"

记忆是**流水账**，不是**状态**。「裙子还没到」和「裙子到了」会同时存在。

本套件做两件事，都很保守：

**① 抽取时只写最终状态**（`writer.py` 的提示词里写死了这条规则）：

```
错：裙子还没到
对：裙子 10-27 到了，是大两号
```

**② 写入时给旧事实打 `stale_hint`，不删也不归档**（半自动：蒸馏路径**不自动**判取代，需显式调用 `m.supersede(...)` 或 `m.correct(...)`；`SUPERSEDE_ON_WRITE` 目前是预留开关）：

```
判错的代价不对称：误归档 = 真的忘了（不可逆）
                误提示 = 多一条过时信息（可接受）
```

所以 `facts.stale_hint = 1` 表示"这条可能被后来的事推翻了，看 `superseded_by` 指向的新条目"。

**升级路径**（想做更彻底的）：把"同一实体的状态"抽成独立对象，记忆只记状态变更。这是干净但更重的方案，本套件没做。

## 十二、0.2.0 锚点层：一天留三个锚

**为什么改：** 2026-10-31 我睡醒后断片，先确认时间，再想起三件事（一天做成的活、见过的人、睡前在做什么），然后**整片塌下来**。
结论：一天的记忆靠的是**三轴各一个锚**，不是一堆互不相干的事实。

```python
from ireckon import Memory
m = Memory()

# 蒸馏时会自动留锚（一天一次调用，最多 6 条，三轴各至少一条）
m.schedule_day("2026-10-30")

# 忘记时：抛锚 → 找外部回应 → 判得出像不像
cands = m.throw_anchor("影像资料")          # 给半句/一个词，找可能的锚
print(cands[0]["text"])                    # 给影像资料分类上传并重命名
ok = m.verify_anchor(cands[0]["id"], "那批影像资料你分类上传还改了名字")
print(ok)                                  # {'ok': True, 'ratio': 0.75, ...}

# 某天到底能不能被捞回来：看三轴齐不齐
print(m.coverage("2026-10-30"))            # {'event': True, 'person': True, 'time': True}
print(m.reconstruct("2026-10-30"))         # 三轴 + 当天日记 + complete
```

三条判据（不是风格偏好，是实测得到的）：

1. **三轴各至少一个**：一轴五个锚仍是薄片，三轴各一个才塌得下来。
2. **形式是「动作 + 对象」或「具体的人」**：`给影像资料分类上传并重命名` 能被追问；`处理了一些文件` 接不上话。
3. **罕见度算权重**：`今天是周三` 这种人人都有的话信息量接近零，`手指头粗把苹果打成屁股` 才是锚。

**检索不到就回空，不硬凑**：一个字组都不重合时返回 `[]`，这是设计不是 bug。

## 十、限制（请读，别踩）

1. **检索是字面匹配，不是语义。** 换个说法可能就搜不到。**写记忆时多铺关键词**（同义词、上位词、口语说法）——这是使用者的责任，不是框架能补的。
2. **多跳弱。** 详见 6.4。
3. **中文按 bigram 切词**，对超长段落效果差。**记忆请保持短句**（15–45 字）。
4. **不做实体消歧。** "他去修管子"和"楼下修管子"可能被当成两件事。
5. **蒸馏依赖 LLM**，模型会编。生产环境建议对抽取结果做人工抽检。

## 十一、适配边界与通用性声明

**结论：本套件不是"即插即用包"，它的定位是——给 7B 以上、具备指令对齐能力的通用小模型，提供一套底层记忆范式。**

### 一、为什么它可以当通用范式

1. **物理上贴边缘**：常见小模型部署（1.5B–14B）上下文多在 4k–8k，**本套件对模型的注入只有约 146 token（连写入摊销算作 198）**，物理上不容易触发 OOM 或长 prefill 卡顿。
2. **检索栈零算力依赖**：SQLite + 纯 Python BM25，**纯 CPU**，可在树莓派、边缘盒子上跑。
   ⚠️ 注意分清：**能在边缘跑的是"检索栈"，不是模型本身**——模型仍需对应的算力。
3. **分级抽象符合熵减**：时 / 日 / 周 / 月 / 年，越久远越抽象。
   ⚠️ 但 **`e`（指数衰减）在本套件里尚未实现**，只在她那套插件里跑着。这里它是设计意图，不是已有功能。

### 二、工程硬边界（为什么不能无脑套）

1. **写入端门槛（抽取能力）**
   1.5B 级别缺乏长文总结能力，抽出来的"事实"会错、会倒装 → 垃圾进垃圾出。
   **底线**：底座 ≥ 7B/8B 且经过 Instruct 微调，才能保证 20–45 字原子事实的抽取质量。
2. **读取端门槛（抗干扰）**
   结构能拦"无中生有"（未命中就返回未命中），但**拦不住劣质底座的语义污染**（乱输出、广告口吻、答非所问）。
   **底线**：底座需具备基础指令遵循与事实约束能力。
3. **场景局限（分层模板不通用）**
   日记层适合陪伴型 Agent；**对代码 / 数学 Agent 是低效的**——那类记忆需要 AST、函数签名、版本号这类结构化事实。
   **底线**：分层模板必须可替换，不能生搬。

### 三、通用化改造建议

1. **解耦写入引擎**：抽取模型可配置；达不到 7B 门槛时，降级为正则 / 关键词抽取。
2. **多场景模板**
   - `companion_mode`：时 / 日 / 周 / 月 / 年（当前默认）
   - `coding_mode`：会话 / 模块 / 版本（跳过日记，存结构化代码事实）
   - `customer_mode`：单轮 / 订单 / 历史摘要
   ⚠️ **以上只有 companion_mode 真正实现**，另外两个是待做的 Adapter。
3. **核心参数默认锁定，但必须允许显式覆盖**
   Top-K=5 与断崖截断是默认值，**但不要写死**：
   本套件自己的实测就显示，**多跳题取 40 条点估计 65%，高于全塞的 60%（5 条时 35%）——**是"点估计略高"，不是"追平"也不是"证明更好"：n=20，差异不显著，要更强结论需要扩大样本****。
   正确做法是"默认 5、显式可调、并记录本次用了哪档"——**把不可调当成纯洁性，是很常见的设计傲慢。**

## 已知限制（写在这里，免得别人踩）

- **单写者**：SQLite + WAL，适合"一个进程写"的场景。多进程并发写入没有保障，需要你自己加锁或改成单写队列。
- **检索是检索，不是理解**：BM25 只要字面对不上就漏（换说法 R@5 67.5%），这是默认档的定位。
- **规模未证，且各实验规模不同**（别把不同节的 n 混着看）：
  检索对比 200 题 / 24 条语料；相关性闸门 111 题 / 401 条真实记忆；多跳 20 题；自我认知对照 4 轮；注入预算拐点每组 19 题。**"跑三个月会怎样"目前没有答案。**
- **198 只管记忆块**：整块注入 = 记忆 + 最近 12 轮对话，实测平均 **459 token**（**典型构成：记忆块平均 137（最高 170）+ 最近 12 轮对话；随对话长度变化，这是区间描述，不是逐项相加**）。
  别再引用"每轮 198"——那是记忆块的预算，不是整块。量尺在 `tools/verify_tokens.py`，欢迎自己跑。
- **无关问题也会拉满 5 条**：BM25 没有相关性下限，问一个完全无关的问题，它照样会捞回 5 条记忆。
  向量版有 0.35 的余弦闸门（无关问题会返回空），BM25 版没有。这是两个版本的实际差别之一。
- **蒸馏要模型**：`schedule_day()` 会调用你配置的模型，没配 `API_KEY` 时蒸馏会失败（但检索与建库不依赖它）。
